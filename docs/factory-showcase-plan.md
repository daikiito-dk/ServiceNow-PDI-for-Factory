# Factory活用プラン — ServiceNowアプリの開発と保守をDroidで自動化する

## 1. 目的

融資事前審査アプリ(Loan Pre-Screening Management)を題材にして、
**「よくある開発作業」と「地味だが欠かせない保守作業」をDroidが継続的に回せる**ことを示す。

見せたいメッセージは次の3つ。

1. **開発**: 要望(チケット)から実装、PDIへの適用、テスト、PRまでをDroidが一貫して行う
2. **品質**: 人が見落としやすいServiceNow特有のバグを、レビューとテストで自動的に止める
3. **保守**: 夜間や定期の点検(構成のずれ検知、回帰テスト、ドキュメント更新)を、人が関わらなくても回す

## 2. 現在の資産(できていること)

| 資産 | 内容 |
|---|---|
| 構成の可視化 | `snapshot_via_browser.py` でアプリ構成を取得し、`docs/app-snapshot.json` と `docs/app-inventory.md` に保存。git diffで変更を追える |
| 構成管理(Infrastructure as Code的な管理) | `app/phase1/manifest.json` とスクリプト本体を、`apply_records.py` でアプリのスコープにべき等に適用できる |
| 実装済み機能 | 入力検証とステータス遷移の強制(ビジネスルール2件とプロパティ1件) |
| 経験値 | スコープ切り替え、GlideElementの比較、`nil()`、スコープ付きロール名などの落とし穴を実際に踏んで解決済み |

## 3. 自動化の前に解消すべき課題

| 課題 | 影響 | 対策 |
|---|---|---|
| **人がいなくても使える認証がない** | 今はブラウザでのログインが必要なので、CIや定期実行で動かせない | PDIに連携専用ユーザー(最小限のロール)を作り、Basic認証またはOAuthで接続する。資格情報はGitHub SecretsやFactoryのSecretsに保管する |
| **PDIの休止** | 一定期間使わないとPDIがスリープし、定期ジョブが失敗する | ジョブの最初に休止を検知し、失敗ではなく「休止中」と報告する。定期的なアクセスで休止をなるべく防ぐ |
| **テストがチャット内のその場限り** | 再現できないので、回帰テストにならない | `tests/` にテストシナリオをコードとして置き、`run_tests.py` で実行する |
| **テストがadminユーザーだけ** | ロールごとの制御を確認できていない | 営業担当と審査担当のテストユーザーを作り、なりすまし(impersonate)かユーザーごとの認証でテストする |
| **フロー本体が未保全** | Flowのノード構成がリポジトリにない | Update Set XMLを取得して `update-sets/` に保存する手順を自動化する |
| **公開リポジトリ** | スナップショットや実データが混入する恐れがある | テストデータはダミー名に限定する。Droid Shield(シークレット検出)とレビューのルールで防ぐ |

## 4. ロードマップ

### フェーズA: 自動化の基盤(1〜2日)

Droidが毎回同じ品質で作業できるように、前提条件を整える。

- **A-1 `AGENTS.md`**: リポジトリのルールを書く(適用前のスコープ切り替え、GlideElementは文字列化して比較、ロールはスコープ付きの名前、変更後は必ずスナップショットとテストを実行、など)
- **A-2 Skill `servicenow-change`**: 「manifest定義 → 適用 → テスト → スナップショット → コミット」の手順をSkillにして、誰が頼んでも同じ手順で進むようにする
- **A-3 連携専用ユーザー**: PDIに作成し、`snow_api.py`(Basic認証)とブラウザ経由の方式を共通の仕組みにまとめる
- **A-4 テストのコード化**: `tests/scenarios/*.json` と `scripts/run_tests.py` を作る。今回チャット内で行った11ケースをそのまま移す。テストデータは最後に必ず削除する
- **A-5 ロール別テスト**: 営業担当と審査担当のテストユーザーを使い、権限による制御を確認する

### フェーズB: 開発の自動化(デモの主役)

- **B-1 チケットから実装まで**: LinearまたはJiraの課題をDroidに割り当てる(Delegations)。Droidはmanifestを変更して適用し、テストを実行してPRを作る
- **B-2 複数機能の一括開発**: フェーズ1の残り(通知とモジュール追加)をMissionsで計画し、まとめて実装する
- **B-3 GitHub Actionsでの適用**: mainにマージされたら `droid exec` またはスクリプトでPDIに適用し、テストを実行する(簡易なCD)

### フェーズC: 品質ゲート

- **C-1 PRの自動レビュー**: Automated Code Reviewを導入する。今回実際に踏んだバグ(GlideElementの比較、スコープなしのロール名、`advanced` フラグの付け忘れなど)をレビュー観点に加える
- **C-2 セキュリティレビュー**: ACLと個人情報(年収)の扱い、公開リポジトリへの機密情報の混入を重点的に確認する
- **C-3 画面レベルのQA**: Droid Controlでフォームを実際に操作し、営業担当では承認できないことなどを、スクリーンショットや動画を証拠として残す

### フェーズD: 保守の自動化(差別化のポイント)

Custom Automations(スケジュール実行やGitHubイベントをきっかけに動く)で次を回す。

| 自動化 | 頻度 | 内容 | 成果物 |
|---|---|---|---|
| **構成のずれ検知** | 毎日 | スナップショットを取り、リポジトリとの差分を確認する。誰かがStudioで直接変更していれば検知する | 差分と説明をまとめたPR、またはIssue |
| **回帰テスト** | 毎日、またはマージ時 | `run_tests.py` を全件実行する | 失敗したら原因の調査結果つきでIssueを作る |
| **健全性チェック** | 毎週 | ACLのないテーブル、無効のまま残ったフロー、使われていないプロパティなどを確認する | レポートか改善PR |
| **ドキュメントの自動更新** | push時 | AutoWikiと `app-inventory.md` を再生成する | Wikiの更新PR |
| **PDIの稼働確認** | 毎日 | 休止していないかを確認する | 休止を検知したら通知 |

### フェーズE: 効果の見える化

- Agent Effectiveness(Analytics)で、PRの数、リードタイム、Droidによる貢献の割合を示す
- 同じ作業を人が手で行った場合との比較表を作る(例: ビジネスルール1件の追加とテストで、手作業X時間に対しDroidはY分)

## 5. デモのシナリオ案(各5分程度)

1. **「要望から本番相当まで」**: 「条件付き承認の理由を記録したい」という課題をLinearに起票する → Droidがフィールド、ビジネスルール、テストを追加する → PRの自動レビューで1件指摘が出て修正される → マージするとPDIに適用されてテストが成功する
2. **「誰かがこっそり変えた」**: StudioでACLを直接変更する → 翌朝、ずれ検知がPRを作り、差分とリスクを説明する
3. **「壊れたら直す」**: わざと遷移ルールを壊す → 回帰テストが失敗する → Droidが原因を特定し、修正PRを作る
4. **「権限を目で確かめる」**: 営業担当ユーザーで承認しようとして拒否される様子を、画面録画で見せる

## 6. 最初のスプリント案(推奨)

フェーズAをすべて行い、デモ2(ずれ検知)を1本動かす。
保守の自動化は他のデモと差がつきやすく、フェーズAの成果だけで実現できるので、最初の成果として見せやすい。
