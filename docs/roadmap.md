# 開発ロードマップ — Loan Pre-Screening Management

> docs/app-design.md §6 の詳細版。現在の実装(2026-10 時点のスナップショット)との
> ギャップに基づく金融系アプリとしての開発計画。

## フェーズ1: 堅牢性(優先度: 高・即効)

| # | タスク | 種別 | 概要 |
|---|---|---|---|
| 1-1 | 入力検証の追加(**完了**) | ビジネスルール | 0円 < 金額 ≤ 上限プロパティ、年収は空欄または0より大きい値、顧客名は必須。PDIで動作確認済み |
| 1-2 | ステータス遷移の強制(**完了**) | ビジネスルール | 受付 → 審査中 →(条件付き/承認/否決)の正しい遷移だけを許可し、変更できるのは審査担当者のみ。PDIで動作確認済み(営業担当ユーザーでの確認は未実施) |
| 1-3 | 通知の追加 | Flow / メール通知 | 新規申請時:審査担当へ通知。二段階承認時:承認者(`approver`)へ承認依頼。結果確定時:申請者へ結果通知 |
| 1-4 | 画面の整備 | モジュール / フォーム | ナビゲーションモジュール追加(現状0件でたどり着けない)。フォームレイアウト・Workspace構成の整備 |

## フェーズ2: セキュリティ・コンプライアンス(優先度: 高)

| # | タスク | 種別 | 概要 |
|---|---|---|---|
| 2-1 | 年収のフィールドレベルACL | ACL | `annual_income` を営業担当から隠す(非表示 or 読取不可)。審査担当のみ参照可 |
| 2-2 | 監査(audit)の有効化 | テーブル設定 | 申請レコードの変更履歴を保全(金融取引の証跡)。`sys_db_object.audit` を有効化 |
| 2-3 | 二段階承認フローの保全 | Update Set XML | Flow ノード構成はRESTで取得できないため、XMLエクスポートで `update-sets/` に保全 |
| 2-4 | 不要構成の整理 | Flow | inactive な「Test」フローの削除 or アーカイブ |

## フェーズ3: 金融機能の拡張(優先度: 中)

| # | タスク | 種別 | 概要 |
|---|---|---|---|
| 3-1 | 与信計算ロジック | スクリプトインクルード | DSR(返済負担率 = 年間返済額 ÷ 年収)算出、金額×年収×格付から自動事前判定、閾値はシステムプロパティ化 |
| 3-2 | 審査ワークキュー | Flow / タスク | 審査担当者間での審査タスク配分とエスカレーション(承認者不在時の代替承認) |
| 3-3 | レポーティング | レポート / ペフォーマンス | ステータス分布、金額帯別承認率、審査リードタイムの可視化 |
| 3-4 | 外部与信API連携 | IntegrationHub / REST | コアバンキング・与信機関APIとの連携設計(本番相当の話。PDIでは設計ドキュメントまで) |

## 実装方式について

- PDIへの変更適用は、ブラウザセッション経由(`scripts/snapshot_via_browser.py` と同じ仕組み、X-UserToken付きREST)で行う。Basic認証の`.env`修正が済めば `inspect_app.py` に一本化可能
- 大きな変更(テーブル変更、フロー)は都度 Update Set XML で `update-sets/` に保全する
- 変更後は必ずスナップショットを再取得して `git diff docs/app-snapshot.json` で意図した差分かを確認する
